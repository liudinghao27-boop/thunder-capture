# 线索采集功能人工测试流程与规范

## 一、目标

建立标准化的人工测试执行体系，确保"线索采集功能"从触发、采集、分类到入队的全链路质量可控，所有阻断及严重级别缺陷在上线前闭环。

## 二、适用范围

- 功能模块：线索采集（Lead Collection）
- 代码路径：
  - `server/api/industries.py`
  - `server/api/jobs.py`
  - `server/workers.py`
  - `core/discover.py`
  - `adapters/mediacrawler/runner.py`
  - `core/classify.py`
  - `server/services/task_stats.py`
- 测试周期：5 个工作日
- 测试覆盖率目标：100%

## 三、角色与职责

| 角色 | 职责 |
|------|------|
| 测试负责人 | 制定计划、分配用例、把控进度、输出报告 |
| 测试执行人 | 按用例执行测试、记录缺陷、截图/录屏佐证 |
| 开发负责人 | 修复缺陷、提供修复说明、协助复现 |
| 产品经理 | 确认业务规则、缺陷优先级仲裁 |

## 四、测试环境要求

### 4.1 硬件环境

- PC：Windows 11，16GB+ 内存，100GB+ 磁盘
- 移动设备：Android 真机或模拟器（用于发送任务验证，可选）

### 4.2 软件环境

- Python 3.12+
- PostgreSQL 14+（或 SQLite 仅用于本地冒烟）
- Redis 6+（用于 Celery）
- Chrome / Edge 浏览器（最新稳定版）
- Playwright 依赖已安装

### 4.3 网络环境

- 生产环境：真实网络 + 有效抖音 Cookie
- 测试环境：沙箱/受限网络（用于异常场景验证）
- 代理环境：住宅代理（可选，用于风控场景）

### 4.4 数据准备

- 有效抖音账号 Cookie（`data/douyin_cookies.json`）
- 测试行业配置：
  - 行业 A：仅关键词（高考志愿）
  - 行业 B：仅 target_users（有效抖音账号 URL）
  - 行业 C：关键词 + target_users 组合
  - 行业 D：空关键词 + 空 target_users（边界）
- 测试账号：普通用户、无权限用户

## 五、测试执行流程

```text
Day 1: 环境搭建 + 冒烟测试
Day 2: 核心业务场景测试
Day 3: 边界/异常场景测试 + 兼容性测试
Day 4: 数据一致性测试 + 缺陷修复跟进
Day 5: 回归测试 + 报告输出
```

### 5.1 每日测试流程

1. **晨会**：确认当日测试范围、依赖是否就绪
2. **环境检查**：
   - 服务启动状态
   - 数据库连接
   - Cookie 有效期
   - 日志目录可写
3. **用例执行**：
   - 按优先级 P0 → P1 → P2 执行
   - 每执行一条用例，立即记录结果
4. **缺陷记录**：发现缺陷立即录入缺陷跟踪表
5. **日终复盘**：汇总当日进度、阻塞问题、次日计划

### 5.2 用例执行标准

每条用例执行时必须记录：
- 用例编号
- 执行人
- 执行时间
- 实际结果
- 通过/失败状态
- 失败原因（如有）
- 截图/录屏路径（如有）

## 六、缺陷管理规范

### 6.1 严重等级定义

| 等级 | 定义 | 示例 |
|------|------|------|
| 阻断（Blocker） | 功能完全不可用，阻塞后续测试 | 采集任务无法创建、任务状态机崩溃、数据库无法写入 |
| 严重（Critical） | 核心功能异常，影响主要业务流程 | 采集到评论但无法入队、任务状态不更新、重复评论未去重 |
| 一般（Major） | 次要功能异常，有 workaround | 前端进度条不刷新、错误提示不明确 |
| 轻微（Minor） | UI/文案问题，不影响功能 | 按钮文字错误、提示信息错别字 |

### 6.2 缺陷优先级定义

| 优先级 | 响应时间 | 修复时间 |
|--------|----------|----------|
| P0 | 1 小时内 | 当日修复 |
| P1 | 4 小时内 | 24 小时内 |
| P2 | 24 小时内 | 48 小时内 |
| P3 | 48 小时内 | 不阻塞上线 |

### 6.3 缺陷记录模板

```markdown
| 字段 | 内容 |
|------|------|
| 缺陷编号 | BUG-XXX |
| 所属用例 | TC-XXX |
| 标题 | 简洁描述问题 |
| 严重等级 | 阻断/严重/一般/轻微 |
| 优先级 | P0/P1/P2/P3 |
| 环境 | Windows 11 + Chrome 125 + 测试环境 |
| 复现步骤 | 1. ... 2. ... 3. ... |
| 预期结果 | ... |
| 实际结果 | ... |
| 截图/录屏 | path/to/screenshot.png |
| 日志片段 | ... |
| 影响范围 | 影响所有采集任务 / 仅影响特定行业 |
```

## 七、测试通过标准

1. 所有 P0 用例 100% 通过
2. 所有 P1 用例 95% 以上通过
3. 无阻断级别缺陷
4. 无严重级别缺陷（已修复并回归通过）
5. 缺陷关闭率达到 100%（或已转为上线后跟进且经 PM 确认）
6. 测试覆盖率达到 100%（所有已识别场景至少执行一次）

## 八、输出物

1. 人工测试用例表
2. 缺陷跟踪表
3. 人工测试执行记录
4. 最终人工测试报告

## 九、风险预案

| 风险 | 应对措施 |
|------|----------|
| 抖音 Cookie 失效 | 提前准备备用 Cookie，测试前每日验证 |
| 网络/平台风控 | 准备住宅代理环境，或改为异常场景测试 |
| 浏览器环境不稳定 | 准备多套 Chrome/Edge 环境 |
| 缺陷修复影响范围大 | 每修复一个缺陷，先执行相关模块冒烟测试 |
| 测试进度落后 | 每日站会调整优先级，必要时缩减 P2/P3 用例 |
