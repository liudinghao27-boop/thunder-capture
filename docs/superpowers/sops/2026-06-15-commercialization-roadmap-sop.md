# 雷霆捕获系统商业化进阶 SOP

> **依据**：`C:/Users/Administrator/Desktop/雷霆捕获系统_客户使用习惯审计报告.md`  
> **当前状态**：阶段 1（数据导出 + 合规模式）已完成并通过测试  
> **目标**：将系统从技术原型转化为可售 SaaS / 可交付商业化产品

---

## 1. SOP 目的与范围

### 1.1 目的

本 SOP 定义雷霆捕获系统从当前技术原型向商业化 SaaS 演进的标准操作流程。它把审计报告中的 P0/P1/P2 改进项分解为可独立交付的阶段，每个阶段都有明确的输入、步骤、输出和验收标准。

### 1.2 范围

- **包含**：产品功能、前端体验、部署方式、合规能力、数据报表、测试与交付流程
- **不包含**：市场营销、销售话术、定价策略、法律诉讼应对

### 1.3 读者

- 产品经理 / 项目经理：按阶段排期和资源分配
- 开发工程师：按 SOP 执行具体实现
- 测试 / QA：按验收标准验证每个阶段
- 客户经理 / CSM：理解每个阶段给客户带来的价值

---

## 2. 总体战略

审计报告评分 **4.05/10**，核心结论是：技术原型 70%，产品化 30%，商业化 15%。

### 2.1 成功路径

```
降低门槛 → 提升上手 → 增强效率 → 数据驱动 → 合规安全 → 云端规模化
```

### 2.2 阶段总览

| 阶段 | 主题 | 覆盖审计优先级 | 预期周期 | 客户价值 |
|---|---|---|---|---|
| **1** | 数据导出 + 合规模式 | P0 导出 / P0 合规 | 1-2 周 | ✅ 已完成 |
| **2** | Web 化配置 + 新手引导 | P1 Web 配置 / P1 Onboarding | 2-3 周 | 降低配置门槛 |
| **3** | 定时发送 + 效果追踪 | P1 定时任务 / P1 效果追踪 | 2-3 周 | 提升自动化与 ROI |
| **4** | 关键词报表 + A/B Test | P2 关键词报表 / P2 文案 A/B | 2 周 | 数据驱动优化 |
| **5** | 移动端适配 + 数据加密 | P2 移动端 / P2 安全 | 1-2 周 | 移动看数、安全合规 |
| **6** | 云端 SaaS 版本 | P0 云端 SaaS | 4-6 周 | 消除部署门槛、规模化 |

### 2.3 依赖关系

```
阶段 1 ──→ 阶段 2 ──→ 阶段 3 ──→ 阶段 4
              │
              ↓
           阶段 5
              │
              ↓
           阶段 6
```

- 阶段 3 依赖阶段 2（Web 化配置是定时/效果追踪的前置 UI 基础）
- 阶段 4 依赖阶段 3（效果追踪数据是关键词/A/B 报表的输入）
- 阶段 6 可与其他阶段并行启动基础设施，但正式交付应在阶段 1-5 稳定后

- [x] 线索可导出为 Excel/CSV

**客户价值摘要**：

### 阶段 2：Web 化配置 + 新手引导

#### 4.2.1 目标

消除 YAML 编辑，让非技术运营人员能在网页上完成项目配置；降低首次上手门槛。

#### 4.2.2 输入

- 阶段 1 完成的合规模式与导出能力
- 现有 `config/industries/*.yaml` 作为字段参考
- 审计报告 3.3/5.2 节列出的配置摩擦点

#### 4.2.3 步骤

1. **字段补齐**：确保 `Industry` 模型包含 `intent_keywords`、`noise_keywords` 等当前仅在 YAML 中的字段
2. **表单化**：在“新建/编辑项目”弹窗中增加表单字段：
   - 意图词（可视化编辑，支持增删改）
   - 噪声词（可视化编辑）
   - 四层关键词漏斗（精准/痛点/行动/子赛道）
   - 回复人设、风格、钩子话术
   - 采集与发送参数（日限额、视频/评论时效等）
3. **智能配置增强**：扩展 `/api/industries/generate-config`，生成的配置包含意图词和噪声词
4. **新手引导**：
   - 首次登录显示 Step-by-Step 引导浮层
   - 就绪度不足时高亮下一步按钮
   - 项目创建后引导“测试一条私信给自己”
5. **术语翻译**：将 `Slug`、`ADB Serial`、`LLM Provider` 等技术术语替换为业务语言

#### 4.2.4 输出

- 后端：扩展的 `Industry` 模型、schema、AI 配置生成 API
- 前端：完整的项目配置表单、新手引导组件、术语文案更新
- 文档：阶段 2 设计文档和实施计划
- 测试：新增/更新单元测试和集成测试

#### 4.2.5 验收标准

- [ ] 用户无需编辑 YAML 即可完整配置一个项目
- [ ] 新用户首次登录看到引导，5 分钟内完成第一个项目创建
- [ ] 所有配置字段保存后能正确用于采集/分类/发送流程
- [ ] `python -m pytest tests/` 通过

#### 4.2.6 风险与回滚

| 风险 | 缓解措施 |
|---|---|
| YAML 与 DB 配置不同步 | 保存时同步写回 YAML 或完全弃用 YAML（推荐后者） |
| 表单字段过多导致用户困惑 | 按“基础/高级”分组，默认折叠高级 |
| AI 生成的意图词质量差 | 提供示例模板和人工复核入口 |

**客户价值摘要**：
> 阶段 2 让非技术运营人员无需理解正则和 YAML，即可在网页上完成项目配置，显著降低客户流失率。

### 阶段 3：定时发送 + 效果追踪

#### 4.3.1 目标

让发送更安全、更可控；建立私信效果反馈闭环（是否被回复、是否转化）。

#### 4.3.2 输入

- 阶段 2 的 Web 化项目配置
- 现有 Celery + Redis 基础设施
- 审计报告 6.2 节列出的工作流断点

#### 4.3.3 步骤

1. **定时任务调度**：
   - 引入 Celery Beat 或 APScheduler
   - 项目级配置：发送时段（如 9:00-21:00）、周末暂停、单日最大发送量
   - 支持“启动矩阵”后自动按时段分发
2. **效果追踪状态机**：
   - 扩展 `TaskQueue` 状态：`pending → sent → replied → converted → failed`
   - 新增字段：`replied_at`、`converted_at`、`reply_text`、`conversion_value`
3. **效果回写机制**：
   - 通过手机 Agent 定期检查私信收件箱，识别对方回复
   - 人工标记“已转化”入口
   - Webhook 推送效果事件给 CRM
4. **前端适配**：
   - 项目配置增加“发送时段”折叠面板
   - 线索池显示“是否回复”“是否转化”列
   - 控制中心显示回复率/转化率

#### 4.3.4 输出

- 后端：定时调度器、效果状态机、收件箱检查任务、Webhook 事件
- 前端：时段配置 UI、线索效果列、转化标记入口
- 文档：阶段 3 设计文档和实施计划
- 测试：定时调度测试、状态机测试、效果回写 mock 测试

#### 4.3.5 验收标准

- [ ] 可设置发送时段，非时段内不发送
- [ ] 周末暂停生效
- [ ] 可标记线索为“已回复”“已转化”
- [ ] 回复/转化数据正确参与转化率计算
- [ ] `python -m pytest tests/` 通过

#### 4.3.6 风险与回滚

| 风险 | 缓解措施 |
|---|---|
| 收件箱检查增加封号风险 | 降低检查频率，使用单独低活跃设备 |
| 定时任务跨时区错误 | 所有时间存储 UTC，前端按用户本地时区展示 |
| 效果数据被用户误标记 | 提供“撤销标记”和审计日志 |

**客户价值摘要**：
> 阶段 3 让客户能够控制发送时段降低封号风险，并追踪私信是否被回复、是否转化，从而计算真实 ROI。

### 阶段 4：关键词报表 + A/B Test

#### 4.4.1 目标

基于效果数据，帮助客户优化关键词和私信文案。

#### 4.4.2 输入

- 阶段 3 的效果追踪数据
- 审计报告 7.2 节缺失报表清单

#### 4.4.3 步骤

1. **关键词效果报表**：
   - 按 `source_keyword` 统计：曝光/采集/发送/回复/转化
   - 前端增加“关键词效果”页面或项目卡片穿透
2. **文案 A/B Test**：
   - 项目支持多个“回复人设/文案变体”
   - 随机分组发送，对比回复率
   - 自动推荐胜出文案
3. **后端聚合服务**：
   - 新增 `server/services/analytics.py`
   - 提供按 keyword / reply_variant / device 的聚合查询
4. **前端可视化**：
   - 柱状图/折线图展示关键词效果
   - A/B 实验列表与结果对比

#### 4.4.4 输出

- 后端：关键词/文案聚合服务、A/B 分组算法
- 前端：报表页面、A/B 实验 UI
- 文档：阶段 4 设计文档和实施计划
- 测试：聚合逻辑测试、A/B 分组测试

#### 4.4.5 验收标准

- [ ] 可按关键词查看转化率排名
- [ ] 可创建文案 A/B 实验并查看结果
- [ ] 报表数据与 TaskQueue 状态一致
- [ ] `python -m pytest tests/` 通过

**客户价值摘要**：
> 阶段 4 让客户知道哪些关键词和文案真正带来转化，把钱花在高效的获客策略上。

### 阶段 5：移动端适配 + 数据加密

#### 4.5.1 目标

让客户能在手机上看数据；提升本地数据安全性。

#### 4.5.2 输入

- 阶段 2-4 完成的前端页面
- 审计报告 4.2/9.3 节对移动端和安全的建议

#### 4.5.3 步骤

1. **移动端响应式适配**：
   - 为控制台添加 Tailwind 响应式类（`md:`、`lg:`）
   - 优先适配：控制中心、线索池、设备状态
   - 导航改为底部 tab 或汉堡菜单
2. **本地数据库加密**：
   - SQLite 使用 SQLCipher 或文件级加密
   - 密钥派生自用户密码 + 盐
3. **API Key 加密存储**：
   - 现有 `server/secret_store.py` 已做部分工作，审计并补强

#### 4.5.4 输出

- 前端：响应式控制台
- 后端/运维：加密 SQLite 方案、密钥管理文档
- 文档：阶段 5 设计文档和实施计划
- 测试：移动端视图测试（可选）、加密/解密测试

#### 4.5.5 验收标准

- [ ] 控制台在 375px 宽度下可用
- [ ] SQLite 文件加密后无法直接读取明文
- [ ] 用户登录后可正常解密使用
- [ ] `python -m pytest tests/` 通过

**客户价值摘要**：
> 阶段 5 让客户在手机上也能监控获客进展，同时保护客户数据不被本地泄露。

### 阶段 6：云端 SaaS 版本

#### 4.6.1 目标

提供注册即用的云端版本，彻底消除部署门槛。

#### 4.6.2 输入

- 阶段 1-5 稳定的功能
- 多租户架构设计
- 部署与运维基础设施

#### 4.6.3 步骤

1. **多租户改造**：
   - 所有模型增加 `tenant_id` 或确认 `user_id` 已隔离
   - 管理员/普通用户角色分离
2. **注册与订阅**：
   - 用户注册、邮箱验证、密码找回
   - 套餐与限额（项目数、设备数、月发送量）
3. **云端部署架构**：
   - Docker Compose / Kubernetes 部署
   - 负载均衡、数据库高可用、Redis 集群
   - 日志聚合与监控告警
4. **设备远程托管方案**：
   - 云真机或客户提供设备两种模式
   - 设备接入认证
5. **合规与法务**：
   - 用户协议、隐私政策、风险知情书
   - 提供“合规版”套餐（只采集不发送）

#### 4.6.4 输出

- 后端：多租户中间件、套餐/限额服务、管理后台
- 前端：注册登录页、订阅页、管理后台
- 运维：云端部署脚本、监控配置
- 文档：阶段 6 架构设计文档和实施计划
- 测试：多租户隔离测试、限额测试

#### 4.6.5 验收标准

- [ ] 新用户注册后 5 分钟内可创建项目并开始采集
- [ ] 用户数据完全隔离
- [ ] 套餐限额正确生效
- [ ] 云端部署可一键启动
- [ ] `python -m pytest tests/` 通过

#### 4.6.6 风险与回滚

| 风险 | 缓解措施 |
|---|---|
| 平台封号导致客户投诉 | 提供封号保险/赔付承诺，强化合规版 |
| 多租户数据泄露 | 全链路审计、数据库行级安全策略 |
| 成本过高 | 按发送量计费，先小规模验证 |

**客户价值摘要**：

## 5. 跨阶段通用规范

### 5.1 分支管理

- 每个阶段从 `main` 切出：`feat/phase<N>-<short-name>`
- 阶段内按任务提交小 commit
- 阶段完成后合并回 `main`（PR 或本地 merge）

### 5.2 数据库变更

- 每个阶段新增字段必须有默认值
- 提供迁移脚本或说明：`server/services/migrations.py`
- 测试环境使用 SQLite，生产使用 PostgreSQL

### 5.3 API 变更

- 新增接口优先，不破坏现有接口
- 所有接口需有 Pydantic schema 和测试
- 认证与权限检查沿用现有 `get_current_user`

### 5.4 前端变更

- 保持现有 Vanilla JS + Tailwind 技术栈
- 所有新增 UI 组件遵循现有 glass-panel 风格
- 关键路径需手动验证

### 5.5 测试要求

- 每个阶段新增测试覆盖核心路径
- 全量测试：`python -m pytest tests/ -v`
- 集成测试必须可脱离 PostgreSQL/Docker 运行
